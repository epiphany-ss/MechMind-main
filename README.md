# 工程力学学习助手：知识网络 / 记忆网络功能开发说明

> 本文档用于帮助项目开发者或 AI 编程助手理解需求、检查现有工程，并在不破坏原有功能的前提下完成“个人知识网络、学习记忆、薄弱点诊断与学习建议”功能。

---

## 1. 项目背景

当前工程已经具备以下核心能力：

1. 用户可以与 AI 进行工程力学问答；
2. 用户可以上传或输入力学结构图；
3. 系统可以根据结构图生成受力分析图；
4. 系统可以根据静态力学图生成运动动画；
5. 系统能够围绕工程力学问题进行解释、推导和辅助学习。

当前缺少的是对学习过程的长期沉淀。用户与 AI 聊完之后，知识、困惑、错误和思考仍然散落在对话记录中，难以搜索、复习和形成连续的个人学习档案。

本功能的目标是：

> 将用户与 AI 的对话、受力图操作、运动预测、练习结果等学习行为转化为可追溯的学习证据，并据此持续更新用户的个人知识网络、学习笔记、能力状态、薄弱点和下一步建议。

---

## 2. 核心设计原则

### 2.1 不是单纯的“聊天总结”

系统不能只把对话压缩成一段摘要，而应从一次学习过程里提取：

- 学习了哪些工程力学概念；
- 用户具体问了什么；
- 用户原来如何理解；
- 用户哪里出现了错误；
- 用户是否真正解决了问题；
- 用户在哪个能力维度上表现较弱；
- 下一步应该做什么练习。

### 2.2 三类数据必须分开

系统中必须区分：

#### A. 工程力学知识图谱

表示客观、稳定的学科知识，例如：

- 约束自由度决定约束反力；
- 受力分析图是建立平衡方程的前置步骤；
- 固定端限制平动和转动；
- 力矩与力和力臂有关。

#### B. 用户个人记忆网络

表示用户真实发生过的学习轨迹，例如：

- 用户问过“固定铰支座为什么有两个反力”；
- 用户曾把“一个支座”误解为“只有一个反力”；
- 用户在一次受力图任务中漏画固定端力矩；
- 用户后来在变式题中成功纠正。

#### C. 用户能力状态

表示用户在不同能力维度上的当前状态，例如：

- 概念理解：基本掌握；
- 结构与约束识别：部分掌握；
- 受力分析：薄弱；
- 方程建立：较好；
- 结果检验：证据不足。

三者不能混在同一张表或同一类节点中。

### 2.3 所有诊断必须可追溯

任何“薄弱点”“错误理解”“掌握状态”都必须关联原始证据，例如：

- 对话消息 ID；
- 用户上传的结构图 ID；
- 用户修改受力图的操作记录；
- 用户的运动方向预测；
- 练习提交记录。

系统不能只输出“你在约束反力方面比较薄弱”，而必须能够说明：

> 最近 4 次固定端相关任务中，用户有 3 次漏画约束力矩，其中 2 次是在 AI 提示后才补充。

### 2.4 不允许 AI 替用户脑补

“我的思考”必须区分：

| 类型         | 含义                 | 是否允许               |
| ------------ | -------------------- | ---------------------- |
| explicit     | 用户明确说过的话     | 允许，尽量保留原话     |
| inferred     | 可从用户原话直接推导 | 允许，但必须标记为提炼 |
| ai_generated | AI 自己联想或升华    | 禁止写成用户思考       |

用户提出问题不等于用户完全不会；用户说“明白了”也不能单独证明已经掌握。

### 2.5 图谱服务于学习，不追求“大而炫”

第一版不要展示包含几百或几千节点的全局网络。默认只显示当前知识点前后 1～2 层关系。

## 3. 第一版 MVP 范围

第一版只需要跑通以下闭环：

```text
用户完成一次工程力学对话
        ↓
系统提取知识点、用户思考、困惑和错误
        ↓
生成一篇可编辑的个人学习笔记
        ↓
更新局部个人知识网络
        ↓
形成一条带证据的薄弱点判断
        ↓
给出一个可执行的学习建议
```

### 3.1 MVP 必须完成

- 保存完整对话及消息 ID；
- 从对话中提取结构化学习信息；
- 生成个人学习笔记；
- 显示当前概念的局部知识网络；
- 记录用户错误和学习证据；
- 基于规则生成薄弱点；
- 显示薄弱点的判断依据；
- 用户可以修改、确认或否定 AI 结论；
- 将受力图操作接入学习事件；
- 为后续运动动画学习事件预留接口。

### 3.2 MVP 暂不实现

- 全课程自动知识图谱生成；
- 复杂 GraphRAG；
- 深度知识追踪模型；
- 自动规划整学期学习路径；
- 不可解释的黑盒掌握度；
- 一次错误就直接判定为薄弱；
- 大型全局“毛线团”关系图。

## 4. AI 编程助手执行要求

在修改工程之前，必须先完成以下检查。

### 4.1 先扫描项目，不要假设技术栈

AI 编程助手应先识别：

- 前端框架；
- 后端框架；
- 数据库类型；
- 用户系统；
- AI 对话调用入口；
- 消息存储结构；
- 图片上传模块；
- 受力图生成模块；
- 动画生成模块；
- API 组织方式；
- 状态管理方式；
- 测试框架；
- 项目代码规范。

不得在未检查工程的情况下直接假设使用 React、Vue、FastAPI、Spring Boot、MySQL、Neo4j 等技术。

### 4.2 优先复用现有模块

实现时应：

- 复用现有用户 ID；
- 复用现有会话和消息记录；
- 复用现有 AI 调用封装；
- 复用现有图片、受力图和动画资源存储；
- 遵循现有路由、服务层、数据访问层和组件规范；
- 避免重写已有聊天功能；
- 避免一次性大规模重构。

### 4.3 推荐实施方式

1. 先输出项目结构分析；
2. 标出需要修改和新增的文件；
3. 给出分阶段实施计划；
4. 先完成数据库迁移和基础模型；
5. 再完成结构化提取服务；
6. 再完成笔记、图谱和薄弱点接口；
7. 最后完成前端页面；
8. 每一步都增加测试；
9. 每完成一个阶段，保证原有聊天、受力图和动画功能仍可运行。

## 5. 建议的数据模型

以下是逻辑数据模型。实际字段名和 ORM 写法应适配当前工程。

---

### 5.1 `concept`

工程力学客观知识点。

| 字段        | 说明                            |
| ----------- | ------------------------------- |
| id          | 主键                            |
| concept_key | 稳定唯一标识，如`pin_support` |
| name        | 中文名称                        |
| aliases     | 别名                            |
| chapter     | 所属章节                        |
| definition  | 简要定义                        |
| description | 扩展说明                        |
| status      | active / deprecated             |
| created_at  | 创建时间                        |
| updated_at  | 更新时间                        |

第一批建议先录入 30～50 个静力学概念。

---

### 5.2 `concept_relation`

客观知识之间的关系。

| 字段              | 说明                   |
| ----------------- | ---------------------- |
| id                | 主键                   |
| source_concept_id | 起点                   |
| relation_type     | 关系类型               |
| target_concept_id | 终点                   |
| description       | 关系说明               |
| confidence        | 关系可信度             |
| source_type       | manual / textbook / ai |
| created_at        | 创建时间               |

建议的关系类型：

```text
prerequisite_of
part_of
applied_to
derived_from
related_to
confused_with
used_in
explains
```

---

### 5.3 `conversation`

如果工程已有会话表，应复用，不重复创建。

最低要求：

| 字段       | 说明     |
| ---------- | -------- |
| id         | 会话 ID  |
| user_id    | 用户 ID  |
| title      | 会话标题 |
| created_at | 创建时间 |
| updated_at | 更新时间 |

---

### 5.4 `message`

如果工程已有消息表，应复用。

最低要求：

| 字段            | 说明                          |
| --------------- | ----------------------------- |
| id              | 消息 ID                       |
| conversation_id | 会话 ID                       |
| role            | user / assistant / system     |
| content         | 文本内容                      |
| content_type    | text / image / diagram / file |
| metadata        | 额外信息                      |
| created_at      | 创建时间                      |

每一项学习诊断都必须能够关联到一个或多个消息 ID。

本功能最核心的事实表。所有学习行为都记录为事件。

| 字段            | 说明                                     |

| user_id         | 用户 ID                                  |

| result          | correct / partial / incorrect / unknown  |
| error_type      | 错误类型，可为空                         |
| evidence_type   | message / diagram / animation / practice |
| evidence_id     | 原始证据 ID                              |
| confidence      | AI 提取置信度                            |
| payload         | 结构化扩展数据                           |
| created_at      | 创建时间                                 |

## 8. AI 结构化提取模块

### 8.1 调用时机

建议在以下时机触发：

- 用户主动结束对话；
- 会话超过一定消息数；
- 用户点击“整理本次学习”；
- 完成一次受力图任务；
- 完成一次动画预测任务；
- 完成一次练习。

MVP 推荐增加明确按钮：

> 整理本次学习

避免每条消息都调用一次大模型，造成成本和状态抖动。

### 8.2 输入内容

输入给提取模型的内容包括：

- 会话消息及消息 ID；
- 用户上传图片的结构化描述；
- AI 识别出的结构和约束；
- 用户对受力图的修改事件；
- 用户是否使用提示；
- 用户是否完成后续练习；
- 已有概念字典；
- 已有错误类型字典。

### 8.4 提取 Prompt

```text
你是工程力学学习记录分析助手。

你的任务不是重新回答问题，而是从用户与 AI 的交互中提取可验证的学习证据，
用于生成个人学习笔记、知识网络、能力状态和薄弱点。

【基本原则】

1. 只记录当前输入中有证据支持的内容。
2. 用户明确表达的内容标记为 explicit。
3. 可以由用户原话直接推导的内容标记为 inferred。
4. AI 单方面解释、用户未确认或未应用的内容，不能作为用户已掌握的证据。
5. 用户提出问题，不等于用户完全不会。
6. 用户说“明白了”，不能单独证明已经掌握。
7. 错误、掌握情况和薄弱点必须关联原始消息或操作 ID。
8. 不得夸大、升华或替用户脑补。
9. 没有证据时返回空数组或 unknown。
10. 优先匹配给定概念字典和错误类型字典，不要随意创建近义重复项。

【需要提取】

- 本次学习主题
```

## 9. 自动笔记模板

系统应由结构化 JSON 渲染 Markdown，而不是让模型直接自由输出最终 Markdown。

```markdown
# 固定铰支座的约束反力
#静力学 #约束 #受力分析

## 核心结论

固定铰支座限制刚体沿两个方向平动，因此通常产生两个方向未知的约束反力，但允许转动，所以不产生约束力矩。

## 相关概念

### [[约束自由度]]

- **定义**：刚体能够独立运动的方式。
- **关联**：被约束的自由度决定约束反力的形式。

### [[固定铰支座]]

- 限制水平方向平动；
- 限制竖直方向平动；
- 允许转动。

## 解题流程

1. 选取研究对象；
2. 判断被限制的自由度；
3. 用正交分力表示未知约束力；
4. 将约束反力画入受力分析图；
5. 根据平衡方程求解。

## 易错点

- 将一个支座理解成只能产生一个反力；
- 错误添加约束力矩；
- 在求解前把未知反力方向当作真实方向。

## 我的思考

> “我原来以为一个支座只能产生一个力。”

[提炼] 我之前把支座数量与约束反力数量直接对应，没有从被限制的自由度出发判断。

## 学习证据

- 对话 `msg_03`：提出“一个支座是否只有一个力”；
- 对话 `msg_05`：能够复述自由度与约束反力的关系；
- 练习 `practice_12`：正确画出两个正交反力。

## 当前状态

- 概念理解：基本掌握；
- 约束识别：部分掌握；
- 受力分析：需要继续验证。

## 下一步建议

完成两道“只判断约束反力，不进行数值计算”的微练习。

## 一句话总结

> 判断约束反力，不看支座有几个，而看它限制了哪些运动。
```

笔记必须支持：

- 编辑；
- 删除错误段落；
- 确认；
- 查看原始证据；
- 重新生成；
- 版本记录。

## 11. 受力分析图接入方式

现有受力图功能不能只保存最终图片，还应记录用户修改过程。

建议记录：

- AI 初始识别的构件；
- AI 初始识别的约束；
- AI 生成的力；
- 用户新增的力；
- 用户删除的力；
- 用户修改的方向；
- 用户修改的作用点；
- 用户修改的力类型；
- 最终是否通过校验；
- 用户是否查看提示。

示例事件：

```json
{
  "event_type": "FORCE_REMOVED",
  "concept_key": "fixed_support",
  "ability_type": "force_analysis",
  "result": "incorrect",
  "error_type": "E01",
  "evidence_type": "diagram",
  "evidence_id": "diagram_action_108",

    "force_type": "reaction_moment",
    "before": "present",

  }
```

## 13. 薄弱点规则

MVP 使用可解释规则，不训练复杂模型。

### 13.1 一次错误不直接判定薄弱

```text
只有一次错误
→ 标记为“需要进一步验证”
```

### 13.2 同类错误重复出现

```text
最近 5 次相关任务中，同一错误出现至少 2 次
→ 标记为“可能薄弱点”
```

### 13.3 依赖提示

```text
用户多次在提示后才能完成
→ 标记为“部分掌握”
```

### 13.4 会说但不会做

```text
能够解释概念
但受力图或方程仍持续错误
→ 概念理解较好，应用能力薄弱
```

### 13.5 问题未闭环

```text
对话结束时仍有未解决问题
→ 标记为“待解决”
不能标记为“已学习”
```

### 13.6 重复犯已纠正错误

```text
错误曾被纠正，后续再次出现
→ 标记为 recurring
提高复习优先级
```

### 13.7 薄弱点评分示例

可以先使用简单规则分数：

```text
weakness_score =
  0.35 × recent_error_rate
+ 0.20 × repeated_error_factor
+ 0.15 × hint_dependency
+ 0.15 × prerequisite_importance
+ 0.10 × forgetting_risk
+ 0.05 × confidence_performance_gap
```

具体权重写入配置文件，禁止硬编码在多个位置。

```text
animation_prediction
variant_problem
```

## 24. 最终产品目标

本功能最终不是为了展示一张复杂的关系图，而是帮助用户回答三个问题：

1. 我之前学过什么；
2. 我具体卡在哪里；
3. 我下一步应该做什么。

产品的核心差异化应是：

> 将 AI 对话、受力分析图和运动动画统一转化为可追溯的学习证据，并据此解释用户的工程力学知识与能力是如何逐步形成的。
